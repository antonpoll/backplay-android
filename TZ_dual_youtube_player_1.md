# ТЗ: Android-приложение "Dual YouTube Player"

## Цель
Личное Android-приложение, показывающее на экране одновременно **два независимых YouTube-плеера** (например, сверху/снизу или слева/справа), которые **звучат одновременно, полной громкостью, без взаимного заглушения**. Один поток — фоновая музыка, второй — подкаст/видео.

Ключевая проблема: по умолчанию Android даёт audio focus только одному приложению/потоку одновременно, из-за чего второй плеер либо ставится на паузу, либо приглушается (ducking). Задача — обойти это в рамках одного собственного приложения.

## Технический риск №1 (важно — прочитать перед началом)
Мы встраиваем YouTube через `WebView` + YouTube IFrame Player API (`<iframe>` с youtube.com/embed на HTML-странице внутри WebView). Воспроизведение `<video>` внутри WebView управляется движком Chromium, который **может сам запрашивать audio focus на уровне ОС независимо от кода хост-приложения** (через MediaSession/AudioManager). Это значит, что простого "не запрашивать AudioManager.requestAudioFocus() в своей Activity" может быть недостаточно — Chromium внутри WebView способен сам себя дефокусировать при появлении второго медиа-элемента.

**Поэтому первым шагом должен быть не полноценный UI, а маленький research-spike:**
1. Создать minimal-проект с двумя WebView на одном экране.
2. Загрузить в каждый простую HTML-страницу с YouTube IFrame API, автоплей двух разных видео.
3. Проверить эмпирически: звучат ли оба одновременно на реальном устройстве, или Android/Chromium всё равно глушит один.
4. Если глушит — пробовать варианты ниже, в порядке возрастания сложности, и на каждом шаге проверять результат перед тем как продолжать.

Не начинать полноценную разработку UI/фич, пока этот вопрос не прояснён экспериментально.

## Варианты обхода (пробовать по порядку)
1. **Ничего не делать с audio focus в коде Activity** (не вызывать requestAudioFocus вообще) — возможно, дефолтное поведение WebView уже позволяет двум WebView звучать вместе, т.к. formально это один процесс/приложение.
2. **Явно указать AudioAttributes с USAGE_MEDIA и запросить AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK** для одного из потоков (не то, что нужно в идеале — даёт приглушение, а не полную громкость, но это fallback).
3. **Обернуть каждый WebView в отдельный процесс** (android:process=":second" в манифесте для второй view) — с отдельным процессом WebView иногда ведёт себя иначе относительно audio focus. Требует IPC между процессами для управления (play/pause/volume), усложняет архитектуру.
4. **Отказаться от WebView для одного из потоков** и воспроизводить через `ExoPlayer` с извлечением аудиопотока напрямую (юридически/технически сложнее, не приоритет).
5. Если ничего не помогает — зафиксировать как известное ограничение и договориться на компромисс (например, второй поток через отдельное реальное приложение типа NewPipe, запущенное в системном split-screen, а не внутри нашего приложения).

## Функциональные требования (после того как аудио-вопрос решён)
- **Экран**: два прямоугольных блока (сверху/снизу, свайпом можно менять пропорции или зафиксировать 50/50 для MVP).
- Каждый блок — WebView с YouTube IFrame Player, с полем ввода/вставки ссылки на видео (paste URL → парсим videoId → грузим).
- Базовые контролы на каждый плеер: play/pause, seek slider, громкость (0–100%) независимо для каждого потока.
- Сохранение последних открытых ссылок между запусками (SharedPreferences или простой JSON-файл).
- Простая история/избранное (опционально, не MVP).
- Минимальный, но опрятный UI — Material Components, тёмная тема по умолчанию.

## Нефункциональные требования
- Целевая версия Android: минимум API 26 (Android 8.0), таргет — последняя стабильная.
- Язык: Kotlin.
- Один Activity, два фрагмента или просто два View в layout — не усложнять архитектуру сверх необходимого, это личный инструмент, а не продукт.
- Разрешения: INTERNET.
- Не встраивать рекламу, аналитику, сторонние SDK.

## Тестовый план
1. Запустить оба видео → услышать одновременно два звука (главный критерий успеха).
2. Свернуть приложение / заблокировать экран → проверить, продолжает ли играть (ожидаемо: WebView может ставить на паузу в фоне — это нормально и не критично для сценария "слушаю с открытым экраном").
3. Проверить поведение при звонке / уведомлении с другим звуком поверх.
4. Проверить на 2+ реальных устройствах если есть возможность (поведение audio focus может отличаться по вендорам/прошивкам).
